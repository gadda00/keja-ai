Section 01
Overview — What This Guide Does

The Keja AI application is built as a static export from the Next.js 16 codebase and served from Vercel's global edge network. On 10 September 2026 production moved from Netlify to Vercel, and the site is live today at keja-ai-rho.vercel.app. This guide walks through the final step of that migration: making the custom domain keja.app (and www.keja.app) serve the exact same deployment at a clean, branded web address.

Because the Vercel side is already fully configured — the project exists, the production deployment is live, and both hostnames are attached to it — the only remaining work is a two-record DNS change at Spaceship, the registrar where keja.app is registered. DNS is the internet's address book: it translates keja.app into server addresses. Right now those addresses still point at the retired Netlify setup; they need to point at Vercel's anycast edge instead. Nothing in this guide touches the application code — the build pipeline already treats https://keja.app as the canonical URL, so no code changes are needed at any point.

How a visitor reaches the site after configuration:

1 · Browser
User types keja.app
2 · DNS lookup
Spaceship resolves the name to Vercel's edge (76.76.21.21)
3 · Vercel edge
CDN matches keja.app to the keja-ai project
4 · Keja AI
App served over HTTPS with auto-SSL
Why the move from Netlify

Two Netlify-side blockers made the old setup impossible to finish: the keja.app apex was claimed by a second Netlify login (a dormant account conflict), and the account was hit by a platform bug that paused production deploys. Vercel needs neither a claim release nor a support ticket — the domain simply points at Vercel's edge via the two DNS records in this guide. The Netlify keja-ai site has been deleted as part of the migration.

Section 02
Before You Start

Completing this checklist first avoids the most common causes of stalled domain setups. Each item takes a couple of minutes to verify, and every one of them has stopped a real deployment at some point, so it is worth being honest about each before touching any DNS settings.

  • The Vercel deployment is live. Open https://keja-ai-rho.vercel.app in a browser and confirm the Keja AI app loads. This is the project's public production URL; the deploy pipeline (GitHub Actions → Vercel CLI prebuilt deploys) ships every push to main automatically. If it does not load, fix the deployment first — domain linking cannot help an unpublished site.
  • You can sign in to Spaceship (spaceship.com) as the owner of keja.app, with permission to edit the domain's DNS records. The domain's nameservers are launch1.spaceship.net and launch2.spaceship.net — DNS is managed in the Spaceship dashboard, and those nameservers stay exactly as they are.
  • You can sign in to Vercel (vercel.com, team Victor's projects) to watch the domain status turn green. Viewing is enough — no Vercel-side changes are needed; both domains are already attached to the keja-ai project.
  • You know whether keja.app currently has live email (MX records for Google Workspace, Zoho, etc.). This guide only changes the A and www CNAME records, so email is untouched — but check anyway, so nothing on the account surprises you.
  • You have up to a few hours of patience. DNS changes usually propagate in minutes, but TTL caching can extend the wait. The .app top-level domain is HTTPS-only (HSTS preloaded), so during propagation browsers will refuse plain HTTP — that is expected behaviour, not a misconfiguration.

Section 04
Step 1 — Update the Two DNS Records at Spaceship

This is the only part of the process that happens outside Vercel, in the Spaceship dashboard. Exactly two records change: the apex A record that currently points at the retired Netlify load balancer, and the www CNAME that currently points at the deleted Netlify subdomain. Both get replaced with Vercel's targets:

TypeName / HostNew Value (Vercel)Replaces (old, Netlify)
A @ (apex) 76.76.21.21 75.2.60.5
CNAME www cname.vercel-dns.com keja-ai.netlify.app
1
Open the DNS editor for keja.app

Sign in to Spaceship and navigate to the DNS management page for the keja.app domain. The record list shows the current Netlify-era entries.

spaceship.com → Domains → keja.app → DNS records
2
Edit the apex A record

Find the A record for host @ (the apex, sometimes displayed as the bare domain keja.app). Change its value from 75.2.60.5 to 76.76.21.21 — Vercel's anycast address, which routes visitors to the nearest edge region. Keep the record type as A; do not convert it to a CNAME (DNS does not allow CNAMEs at the apex).

3
Edit the www CNAME record

Find the CNAME record for host www and change its target from keja-ai.netlify.app to cname.vercel-dns.com. If the editor shows a trailing dot (cname.vercel-dns.com.), that is fine — registrars treat both spellings identically. If the editor rejects the change, look for a conflicting pre-existing A or AAAA record on www and delete it first.

4
Save and leave everything else alone

Save both edits. Do not change the nameservers (launch1/launch2.spaceship.net stay), and do not remove other records (email MX, SPF TXT, and so on) — this migration only repoints web traffic. TTL can be left at its default; lowering it beforehand only helps if you expect to roll back quickly.

Why only these two records

The apex domain cannot be a CNAME (DNS does not allow it), so it points at Vercel's edge IP 76.76.21.21. The www subdomain can be an alias, so it points at Vercel's CNAME target. Vercel also publishes a TXT verification record (_vercel.keja.app) as an alternative ownership proof — it is not needed when the A record points at Vercel, so you can ignore it.

Section 05
Step 2 — Verify Propagation

DNS changes ripple outward from Spaceship's nameservers, usually within minutes. Verification is a pure read-only operation — run these commands from any terminal (or use an online dig tool) and compare against the expected values: 

# 1. The apex must resolve to Vercel's anycast address
dig +short keja.app A
# expected: 76.76.21.21

# 2. www must alias to Vercel's CNAME target
dig +short www.keja.app CNAME
# expected: cname.vercel-dns.com.

# 3. The site must answer over HTTPS with Vercel headers
curl -I https://keja.app
# expected: HTTP/2 200 + an x-vercel-id response header

# 4. www must redirect to the apex (308)
curl -I https://www.keja.app
# expected: HTTP/2 308 + location: https://keja.app/

In the Vercel dashboard, open keja-ai → Settings → Domains: the status next to keja.app and www.keja.app changes from "Pending" / "Invalid Configuration" to a green Valid Configuration once the records resolve from Vercel's point of view. The certificate is issued at the same time — if the dashboard still shows pending but dig is correct, give it a few more minutes; Vercel re-checks automatically.

Certificates need a little time

In the minutes right after the switch you may see a TLS warning on keja.app — the DNS has moved but Let's Encrypt is still provisioning the certificate. This self-heals within about an hour and usually within minutes. Do not "fix" it by changing DNS again; just re-test after a short wait.

Section 06
What Vercel Handles Automatically

Once the two records resolve, no further configuration exists anywhere — the remaining behaviour is baked into the project. It helps to know what to expect, so none of the following comes as a surprise:

  • HTTPS everywhere, always. Let's Encrypt certificates for keja.app and www.keja.app are issued automatically and renewed behind the scenes — no expiry warnings, nothing to schedule. Plain-HTTP requests are upgraded to HTTPS at the edge.
  • www folds into the apex. www.keja.app is configured as a redirect domain: it answers with a permanent 308 to https://keja.app, keeping a single canonical URL in search results and analytics.
  • Every deploy updates the domain. Each green deployment is promoted to production and instantly serves from keja.app — no alias updates to run. keja-ai-rho.vercel.app keeps working as a permanent fallback URL.
  • Monitoring is already watching. The repository's production-check workflow smoke-tests keja.app hourly once it is live — its Actions badge turns green for the domain when the switch has propagated.
Section 07
Post-Launch Checklist

After curl -I https://keja.app answers 200, run through this list once to confirm the whole surface works end to end. It takes about five minutes and covers everything the domain switch could possibly affect:

  • App loads. Browse https://keja.app — search, listings, and the AI advisor all work; deep links like https://keja.app/#/properties/KJA-001 open the right views.
  • Redirect works. https://www.keja.app lands on https://keja.app with a padlock in the address bar.
  • PWA installs. On Android, Chrome offers "Install app"; on iOS, Safari → Share → Add to Home Screen. The installed app launches full-screen with the Keja splash.
  • Offline shell works. With the app installed, airplane-mode launch still shows the cached shell (the service worker version is stamped per build, so the next online visit picks up updates within a day).
  • Repo monitors go green. GitHub → Actions → Production check shows both matrix entries passing (production alias + keja.app).

Almost every failure mode of this setup is a propagation or stale-cache variant. Work down these tables before changing anything — most rows resolve by waiting, and unnecessary edits to DNS only extend the outage. The first table covers the DNS layer (records, certificates, Vercel's view); the second covers what users see on their devices after the DNS is already correct.

Rollback path

If anything needs undoing, the change is fully reversible: point the A record back and the www CNAME back to their previous values. Vercel keeps every production deployment, so code-level rollbacks never touch DNS — dashboard → keja-ai → Deployments → any green build → Promote to Production.

If a problem persists beyond this table, the fastest escalation paths are, in order: the repository's engineering runbook (docs/DEPLOYMENT.md) which documents the exact live configuration this guide mirrors; the Vercel dashboard's deployment and domain logs, which show edge-side errors that DNS tools cannot see; and Vercel support itself, reachable from the dashboard's help menu — the Hobby plan includes it for exactly this kind of account-level question. In practice, though, every issue seen so far with this setup has been a propagation window that closed on its own.
